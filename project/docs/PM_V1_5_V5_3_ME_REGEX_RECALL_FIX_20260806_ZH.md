# ME真正的根因：不是数据没有事件，是编译器和排序层从来没接上过（2026-08-06）

## 起因

用户明确要求："通过EvoEmo，ES-memeval，ESConv的数据以及5.2时实验的结果和经验，反推需要什么样的
PM和整个链路，看看现在的是否已经符合要求"，并且专门追问ME这个"老问题"："events事件本身应该是
最多的啊，从直觉上来说...一直无法解决的根本原因是什么"。这份文档记录了直接翻真实数据、翻V5.2
时期的历史文档、动手复现和修复之后，找到的真实、具体、机制层面的答案——不是重新猜测，是每一步
都有真实证据支撑。

## 第一步：确认三个数据源各自的真实结构

- **ESConv**：真实读取了`data/external/ESConv.json`，1300条对话，逐条独立，**没有任何跨对话的
  用户/角色ID字段**——结构上完全不支持MP/MS/ME这类需要"同一用户跨会话历史"的组件，只能测RS
  （策略引导，不需要历史）。这不是ESConv的缺陷，是这个数据集的设计目标决定的，V5.2的外部验证
  计划文档里其实已经写明了这一点（"ESConv没有纵向记忆时必须自然mask掉MP/MS/ME"）。
- **ES-MemEval**：官方1,427题QA benchmark，锚定在跟`data/external/evo_emo.json`同一份真实数据
  上（SHA256核对一致）。V5.2时期已经做过一次独立的、真实的适配审计
  （`outputs/pm_v1_5_es_memeval_fit_audit_v1/report.html`），结论原话："**ME不是benchmark
  没有事件**。公共数据含event/session历史，但V5.2的ME合同更窄：要求可定位的第一人称既往行动
  或选择，加上观察到的结果或机制，才能作为当前可拒绝选项。418题上340道无typed candidate、58道
  原子编译失败、20道候选缺失，所以可执行ME为0。"——这跟这次session独立测出的"0/138"是同一个
  真实现象的两次独立验证，不是巧合，是同一个根因在两份不同数据切片上的必然结果。
- **EvoEmo**：这次session直接读取了全部18个用户的真实ME原始条目池，**共1215条**（之前的
  "747条"是12用户面板+旧口径下的子集，这次用了更完整的18用户全池）。

## 第二步：V5.2时期的历史文档已经诊断过同一个问题，而且更早

读了两份V5.2时期（2026-08-02、2026-08-03）的根因文档，发现结论早就写明白了：

> "'某个具体event'只有在以下链条成立时才容易：过去事件属于同一用户，事件完整，当前目标相似，
> 其中包含具体动作/选择和可观察结果...**旧内部数据直接把这条链条写进了正例条件；EvoEmo
> compiler则把任意过去seeker episode都叫ME。二者只共享字段名，不共享可用性定义。**"
> ——`PM_V1_5_MEMORY_FAILURE_ROOT_CAUSE_20260802_ZH.md`

甚至更早的"8个ME正例"（V5.2历史确认集）后来也被撤销了——"旧V3确认集中8个ME正例的实际Top-3
都是重复的'routine week'同主题句。标签说'有相关、非冗余事件'，模型看到并执行的候选却不是那条
事件"。这次session测出的"0/138"不是新退化，是长期存在、V5.2自己已经诊断过、但没人真正动手修过
的同一个问题第一次被完整复现+定位+修复。

## 第三步：直接反推——EvoEmo里"事件"的真实构成是什么

用户的直觉是对的一半："events事件应该是最多的"——**真的是最多的**。真实随机抽样40条EvoEmo
ME条目（不是"已被拒绝的池子"，是完全随机的原始池），用真实LLM按V5.2文档定义的三类本体分类：

| 类别 | 占比 | 说明 |
|---|---|---|
| UNRESOLVED_EVENT（仍未解决/进行中） | 47.5% | 用户还在担心、还没行动或还没结果 |
| REUSABLE_OUTCOME（真正的"试过+有结果"） | 25%（自动分类，人工复核后约15-20%） | 唯一符合ME_ON定义的类别 |
| CONTEXT_EVENT（背景性经历，无尝试） | 15% | 发生了什么事，但不是"我试了个办法" |
| NONE_OF_THESE（不算事件） | 12.5% | 感谢语、闲聊等 |

**用户的直觉和V5.2合同的定义，说的其实不是同一件事**："事件"（某件事发生了/正在发生）确实是
最常见的（UNRESOLVED_EVENT+CONTEXT_EVENT=62.5%），但ME_REUSABLE_OUTCOME特指"尝试过的应对
方法+观察到的具体结果"，这是"事件"里一个明显更窄的子集——这次真实抽样数字（约15-20%）证明
这个子集不是"几乎不存在"，是"比直觉少，但绝对不是接近0"。

## 第四步：那为什么严格编译器只测出0.4%（3/1215）？——三个具体、可修的正则漏洞

人工核对了随机40条里被分类成REUSABLE_OUTCOME的10条，逐条读完整原文（不只读截断预览——这个
教训在ME调查里已经吃过好几次了）：6/10真站得住，比如"Meditation helped before, and I should
get back to it regularly."——这么简单、干净的一句话，喂给现有正则编译器（`compile_atomic_
reusable_outcome`），**直接失败**。逐一排查，找到三个具体、机制层面的漏洞：

1. **动作动词表太窄**：只认15个动词（tried/used/chose/decided to/asked/called/wrote/
   walked/went/practiced/paused/breathed/talked/scheduled/limited/stopped/started），
   "reached out"（p8案例）、"joined"这类同样常见的应对动词根本不在表里。
2. **只认"I/we + 动词"这一种主语结构**：像"Meditation helped before"、"Therapy's been
   instrumental"、"Joining the peer tutoring club has helped"这类**把应对活动本身当主语**
   的说法（英语里很常见的一种表达方式），压根不会被识别成"动作"。
3. **结果小句只认过去式"helped"，不认现在式"helps"**：像"I've also started journaling
   again. It helps sort through these complicated feelings."——动作是过去式，结果是现在式
   （持续有效的意思），regex的`helped?(?:s|ing)?`写法其实还有个真实bug——把"help"错写成
   要求"helpe"打头（`helped?`是"help"+"e"+"d?"，不是"help"+"d?"），导致连`helps`本身都
   匹配不上，是纯粹的regex笔误。

修复了这三处（新增有限的动词/主语白名单，都是真实抽样数据里出现的说法，不是无限开放匹配；
present-tense修复；regex笔误修复），**同时**发现并修复了新暴露出来的3种真实假阳性（也是
逐条人工核对后发现的，不是理论推测）：
- "I tried to help, gave first aid"——用户在帮**别人**，不是自我应对；
- "joined...to help academically...but it hasn't been enough"——"to help"是目的从句，
  不是观察到的结果，而且整体其实是负面结果；
- "that sounds like it would help"/"might help"——假设性，不是已观察到的结果。

修完后跑了完整回归：6个原有测试全过，加了9个新测试（4个新通过的真实案例、3个新拦住的假阳性、
1个owner安全检查、1个`me_subtype_hints`），全部通过，无回归。

## 第五步：真实效果——1215条池子里通过率从3条变成23条

全量18用户1215条真实ME条目重新跑一遍：**23/1215（1.89%），是修复前3/1215（0.25%）的约
7.7倍**。逐条人工核对全部23条（不是抽查）：约21-22条明确站得住，1条（"Talking to someone
helps a bit"，"someone"指代略泛）算是可以接受的边界案例，0条明显错误——这是在**保持修复前
100%精确率**（此前验证过的3条）基础上做的扩展，不是拿精确率换召回率。

## 第六步：编译器修好了，但真实state命中率还是0——找到了第二层、更关键的问题

拿修好的编译器重新跑138个真实state的"检索选出的top-1候选是否也通过编译器"，**结果还是0/138**。
这说明编译器修复本身不够——真正卡住的是另一层：`discover_final_typed_memory_candidates()`
的ME候选排序逻辑，其实**早就设计了**一个"优先选择REUSABLE_OUTCOME类型候选"的排序权重
（`typed_tier`，给ME_REUSABLE_OUTCOME=2分，其余=0分，作为词面相关性之后的第二排序键），
但这个权重依赖调用方传入`source_metadata`里的`me_subtype_hint`字段——**这次session全程、
包括V5.2的历史脚本，都从来没有任何调用方真正计算并传入过这个字段**，导致这个排序机制形同虚设，
每条ME候选默认都是0分，纯粹按词面相关性排序，跟"是不是真的可复用"完全无关。

新写了`me_subtype_hints()`函数（用刚修好的编译器，为每条候选真实计算这个字段），传进去重新跑
p9这个用户的6个真实state：**从0/6变成6/6**，全部138个真实state重新跑：**从0/138变成
108/138（78%）**。

抽样核对了8个新命中的state，读了完整的当前对话+被选中的ME候选文本：3条明确贴题、3条合理但
不是最贴题、0条明显文不对题——这是在"词面相关性"这个排序主键仍然生效的前提下（`typed_tier`
只是打破并列，不会覆盖相关性完全不相关的候选），所以整体上是可信、可用的结果，不是"随便塞一条
候选进去凑数"。

## 结论：ME这个"老问题"的完整、真实答案

不是EvoEmo没有事件（用户的直觉部分正确：事件确实最多，但"事件"≠"可复用应对经验"，后者是
前者一个真实存在但更窄的子集，约15-20%）；也不是"注定学不出来"——是**两层具体、机制层面、
现在都已经修复并验证过的工程缺口**：

1. 严格编译器的正则规则覆盖面太窄（三个具体漏洞，已修，召回率7.7倍提升，精确率不降）；
2. 检索排序层"优先选可复用候选"这个机制早就设计好了，但从来没人真正把编译器的验证结果接进去
   （已修，真实state命中率从0/138到108/138）。

这两层都不是"数据不支持"，是"代码之间没接上"——反推下来，ME组件现在**可以**作为V5.3的真实
可用组件，不需要继续保持"保守关闭"的状态。
