# 历史诊断：旧 PMV2 后端与 EvoEmo 的候选级特征差距（2026-08-06）

> **重要范围更正（2026-08-06）**：本文所谓“训练域”实际来自已经淘汰的 468-card PMV2
> backend，不是当前 V3 exact Rank-1 effect construction，更不是尚未生成的 V5.3 FIT。
> 因而本文 `past_action_result=0%` 只证明旧 backend 不能拿来训练新的 ME head，不能证明当前
> 正式构造没有 ME 支持。当前构造的零 API 复核显示：128/128 个 effect state 的 exact Rank-1
> ME 候选均通过同一 compiler 并正确绑定。当前结论见
> `PM_V1_5_V5_3_ME_CURRENT_CONSTRUCTION_SUPPORT_AUDIT_20260806_ZH.md`；本文保留为历史诊断，
> 不再作为 V5.3 readiness 证据。

**2026-08-06后续更正**：独立审核指出`incremental_injected_tokens`/`age`这几个字段名字
叫"候选级特征"，实际计算时用的是`describe_memory_candidate()`对整个`selected_items`
（可能包含最多3条ME候选，不是只有真正会被注入的那1条）的聚合统计，不是真正exact
Rank-1候选自己的值。核实过是真的：训练域`selected_items`平均只有1.14条（149/216是1条、
30/216是2条），EvoEmo域**恒定是3条**（top_k=3，EvoEmo候选池够大总是能填满）——这个
系统性差异会虚高聚合类指标的差距。**已修复**（`v1_5_v5_3_contribution_slot_features.py`
拆成`rank1_*`——只用`selected_items[0]`单独计算——和`topk_*`——保留原有的Top-k聚合
诊断，明确改名不再混称）。**`past_action_result`这个最核心的发现完全不受影响**（它本来
就只读`selected_items[0]`），但token成本的差距从虚高的"7倍"修正为约"2.5倍"（真实注入
的单条候选：训练域均值37 token，EvoEmo域均值92 token）。下文数字已更新为修正后的版本。

## 本文仍能回答的窄问题

之前测的两件事都不是这个问题本身：`PMV2FeatureBuilder`的OOD测的是要被淘汰的旧目录统计
表示；检索器压力测试测的是"找不找得到候选"。这次（`60_contribution_slot_domain_
comparison_v1_5.py`）用真正会喂给Step1的候选级特征（`contribution_slot`，昨天刚实现，
commit `611e75e`），对同一个真实检索出来的top-1候选，在训练域（179个真实内部state）和
EvoEmo域（138个真实state）之间直接对比分布。

## 结果：多个维度存在真实、可信、有些相当严重的差距

| 特征 | 训练域 | EvoEmo域 | 差距 |
|---|---|---|---|
| `past_action_result`（候选是否真通过ME编译器，**exact Rank-1**） | **0.0%** | **78.3%** | **严重** |
| `rank1_injected_tokens`（**修正后：只算真正注入的那1条候选**） | 均值37 | 均值92 | 约2.5倍 |
| `rank1_relative_age`（**修正后：只算exact Rank-1**） | 均值0.22 | 均值0.34 | 明显 |
| `topk_capacity_fraction`（Top-k诊断，非exact Rank-1） | 恒定0.667（零方差） | 恒定1.0（零方差） | 确认，无重叠 |
| `topk_top1_lexical_relevance`（Top-k诊断） | 均值0.22 | 均值0.48 | 约2倍 |
| `topk_top1_top2_lexical_margin`（Top-k诊断） | 均值0.14 | 均值0.02 | 反向7倍 |
| `current_redundant` | 42.5% | 13.0% | 明显 |
| `current_action_invitation` | 0.0% | 0.0% | 两边都是0（见下） |

## 最严重的一项：`past_action_result`——训练域永远是False

抽查确认不是脚本bug：直接读了一个真实训练卡片的原始ME条目，两条都不通过编译器——一条是
"in one prior episode involving X, wrote down the hardest moment before responding and
later felt less overwhelmed."（内部语料自己的"正例"模板），另一条是纯背景描述。这正是
昨天已经发现过的同一个根因（内部ME"正例"模板本身不满足自己的编译器合同），**这次是第一次
在真正会喂给Step1的候选级特征层面上，量化确认了这个问题的严重程度：整个训练域，没有一个
真实state的top-1候选通过编译器**。这意味着如果真的拿这批数据训练ME的value head，模型在
`past_action_result`这个维度上**永远学不到任何东西**——这个维度在训练时恒为0，模型没有
理由认为它重要，但部署到EvoEmo时这个维度78.3%是True，恰好是最该依赖的信号之一。

## 追查：只修模板文字够不够？——做了一次诊断性复算，答案是"有帮助，但不够"

**不修改任何真实文件**，只在内存里把内部语料的"正例"模板文字，换成昨天已经验证过通过
编译器的正确写法（"When dealing with X, I wrote down the hardest moment before
responding, and it helped me feel calmer."），其余（检索、排序、目录规模、案例数量）全部
不变，重新跑一遍：

- 216个训练state里，192个的ME目录**确实含有**这条模板（说明这个模板覆盖了内部语料
  绝大多数卡片，改一个模板字符串影响面很大）；
- 但top-1候选真正通过编译器的比例，只从**0%提升到16.7%**——远没有到EvoEmo域的78.3%。

**说明这不是单一原因**：模板文字确实是一个真实、可修的问题（改了就有真实提升），但**检索
排序本身也有贡献**——即使某张卡片的信号条目文字改对了，排序也不一定把它排到第一（很可能
是因为一张卡片内的两条ME条目经常对应不同的具体话题，排序更看"跟当前这轮话题贴不贴"，
不是"哪条更符合ME_REUSABLE_OUTCOME这个构念"，`me_subtype_hint`只是打平后的二级排序键，
救不了主键选错话题的情况——这跟检索器压力测试V1最初的错误结论其实是同一个机制，只是这次
出现在真实、未经人为构造的训练数据里，是真实存在的、不是测试构造出来的假象）。

## `current_action_invitation`两边都是0%——不是没有差距，是这个信号本身太窄

复用的`observable_flags()`（今天为RS验证过的同一个函数）在训练域和EvoEmo域上都几乎从不
触发。这不是训练/EvoEmo之间的差距，是这个正则本身校准得太窄（只认"what should I do"、
"any advice"这类非常具体的措辞），**两边都测不出来，等于这个槽位目前对ME几乎没有用**，
需要要么放宽正则、要么换一个更鲁棒的意图判断方式，不能直接拿现在这版当有效特征用。

## 结论：泛化问题是真实的，但现在有了精确、可执行的修复方向

不再是笼统的"训练数据不够多样"，是三个具体、独立、优先级不同的真实问题：

1. **内部语料的ME正例模板文字需要修**（便宜，改一处模板字符串，覆盖192/216张卡片，
   已验证有真实提升但不够）——这是第一步，成本最低；
2. **检索排序在"话题贴合度"和"构念正确性"之间的优先级需要重新设计**——`me_subtype_
   hint`目前只是打平后的二级排序键，主键（词面话题相关性）选错话题时救不回来，这需要
   要么让候选构造本身保证同一张卡片内的信号条目匹配当前查询的话题，要么把`typed_tier`
   的权重提到比纯话题相关性更高（后者是一个真实的排序算法设计决策，不是数据问题）；
3. **`current_action_invitation`这个正则需要重新校准或换方法**——现在两边都测不出来，
   等于没有提供真实信号。

这三项都不是"训练数据规模不够多样"这个说法能概括的——是三个不同层面（内容模板、排序
算法、意图识别）的具体问题，各自成本不同，可以独立推进。

## 对之前结论的更新

这次发现不推翻之前"检索器在真实规模下基本可靠"（V2压力测试）的结论——那次测的是"候选
存在且合同正确时，检索器找不找得到"，答案仍然是"找得到"。这次发现的是**训练语料自己的
候选内容本身，在很大比例上根本不满足ME的合同**，是内容生成层面的问题，不是检索算法本身
在真实规模下失效。两个发现互相独立，都是真的。
