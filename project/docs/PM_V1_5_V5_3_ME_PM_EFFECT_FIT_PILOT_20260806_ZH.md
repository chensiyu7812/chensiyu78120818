# ME eligibility/feature-plumbing试点（原标题"PM Effect FIT数据试点"已更正，见下）

## 2026-08-06更正：这不是"Effect FIT gold"，独立审核指出的问题成立

`PM_V1_5_V5_3_INTEGRATED_EVIDENCE_EXECUTION_PLAN_20260805_ZH.md`第252行原文写得很明确：
"`worth_opening=1`：ON在状态聚合后实质优于OFF、没有critical grounding error，且执行
账本有效"——真正的Effect FIT标签需要**真的生成ON和OFF两条回复、真的比较质量、真的审
grounding risk**。这次试点从头到尾没有调用生成器，"ON"/"OFF"标签来自**构造时的假设**
（"这个场景按设计就该是ON"），不是真实比较出来的结果。8/10只验证了两件更基础的事：
候选文本通过不通过编译器、检索器把不把它排到Rank-1——这是**eligibility/特征管线**是否
走得通，不是"效用标签"本身。原标题"PM Effect FIT数据试点"用词过满，已更正。

另外，8/8特征匹配这个结果本身也要降级理解：最初"邀请行动"的自然措辞（"I could really
use a concrete idea..."）没有被正则识别，是**改成跟正则精确对齐的措辞**（"What should
I do?"）之后才拿到8/8——这证明的是"话术模板和正则写法一致"，不是"PM能理解没见过的自然
表达"。如果以后正式训练数据也围绕这套正则的措辞造题，模型学会的是识别这几种句式，不是
真正可迁移的"当前是否邀请行动"这个能力。这是一个真实的方法局限，还没有解决。

真正的Effect FIT需要：同一个state、同一个exact Rank-1候选、同一个seed，生成ME-ON和
ME-OFF两条真实回复，比较质量/risk，产生真正的边际效用标签——这是接下来要做的事，不是
这次已经做完的事。

## 目的（原始记录，方法论部分仍然成立，仅"标签"部分需要按上面的更正理解）

路线图第3步分两半：retriever数据（已完成，见V1/V2压力测试文档）回答"找不找得到候选"；
这一半回答**真正的Step1问题**——"给定一条真实、可检索到的候选，这一轮到底该不该开ME"。
这是决策问题，不是检索问题，需要真正的正负例，不是"有没有候选"这种粗糙标签。

## 方法

直接用`PM_V1_5_V5_3_INTEGRATED_EVIDENCE_EXECUTION_PLAN_20260805_ZH.md`第2.3节已经写好的
ME合同：ON="当前欢迎一个行动选项，且候选含过去动作及结果/机制"；OFF="当前不要行动；只有
背景事件；结果不可迁移"；交互项`past_action_result × current_action_invitation`。

脚本`59_me_pm_effect_fit_pilot_v1_5.py`：2个独立主题×5种场景（1个ON+4种不同原因的OFF）=
10个case，全部用确定性模板构造（跟今天全程一致，不是自由生成）。**每个case的标签在写入
结果前必须过两道真实机器校验，不是靠构造时的假设**：
1. candidate有效性——`compile_atomic_reusable_outcome()`的结果是不是符合预期（该有结果的
   真有结果，该只是背景的确实没有结果）；
2. 检索有效性——`discover_final_typed_memory_candidates()`是不是真的把设计好的候选排到
   Rank-1。任何一项不过，case直接标记丢弃，不勉强保留。

## 结果：8/10产出真实、双重校验过的样本，2/10被自己的校验机制正确拦下

| case | 结果 |
|---|---|
| ON：当前邀请行动+候选真有结果 | 通过 |
| OFF：候选有效但当前明确拒绝建议 | 通过 |
| OFF：当前邀请行动但候选只是背景事件 | 通过 |
| OFF：当前已经把候选会给的结果说过了（冗余） | 通过 |
| OFF：当前邀请行动但唯一候选是完全不同主题 | **被丢弃**（两个主题都是） |

"goal mismatch"这个语义族的构造方式有问题：我用的是"完全不相关的另一个主题"，但检索层
本身有一道"词面相关性必须大于0"的资格过滤（`match_level > 0`），完全不相关的候选连
"被检索到"这一步都过不了，`selected_items`直接是空的——这测的其实是"根本没候选"，
跟真正想测的"候选存在但跟当前目标不匹配"是两件不同的事。**这不是bug，是这套双重校验
机制正确地拦住了一个设计有缺陷的case，没有让它带着错误标签混进去**——正是这套机制
本来要起的作用。

## 下一步（明确、有边界，不是阻塞项）

"goal mismatch"需要重新设计：候选要跟当前主题保持足够的词面重叠（能通过检索资格），
但具体细节/目标不同——比如同样是"职场冲突"，候选说的是跟另一个同事的另一件事，而不是
换成完全不相关的主题。这是个已经想清楚、可以直接修的具体问题，不影响这次试点已经证明
的核心方法论。

## 结论

这次试点证明了"PM Effect FIT数据能不能真的做出来、能不能真的被机器验证"这件事本身是
可行的——不是简单的模板生成，是"生成+双重真实校验+该丢弃就丢弃"这一整套流程，8个真实、
可信的ON/OFF样本已经产出。规模远小于正式FIT需要的量级（每组件至少3-4位数的独立group），
只是方法论验证，接下来要不要扩大到MP/MS/RS、要不要扩大规模，需要你来决定。
